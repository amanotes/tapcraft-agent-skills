# TapCraft

TapCraft runs many games inside one shared Cocos engine. A normal Cocos solution can break the hub or the next game. **The TapCraft contract overrides generic Cocos defaults** for assets, content loading, lifecycle, exit, storage, platform services, engine modules, build settings, performance, and publishing.

## Start every TapCraft task

1. Run the bundled read-only version check:

   ```bash
   node <skill-directory>/scripts/check-updates.mjs
   ```

   It must not update the plugin, install packages, or edit the game. Work offline when the check cannot reach GitHub or npm.
2. Inspect `package.json`, `game.json`, and the current build before proposing changes.
3. Baseline contract: `com.amanotes.tapcraft-kit` **2.0.0**, also the minimum (SDK 2, protocol 2), Cocos Creator **4.0.0-beta.1**, engine profile **8ec328**. Kit 2 replaces kit 1.x (`platform`, `saves`, AmaGDK) with one facade, `Tapcraft`. A game on kit 1.x is hidden by the 2.0 app until it is ported, rebuilt and republished: read [references/kit-2-migration.md](references/kit-2-migration.md) (saves are not migrated). Prefer a newer stable kit only after reading its changelog and confirming compatibility with the installed TapCraft app. Ask before changing an existing dependency.
4. Read only the references required by the task.

## Non-negotiable overrides

### Assets and content

- Game code uses `Tapcraft.content`; do not call `assetManager.loadBundle` or invent another loader.
- Every Cocos asset belongs to a bundle. Keep boot, menu, first gameplay, shared UI/SFX, and everything needed in the first 30 seconds or offline in local bundles. Put later content in remote bundles.
- Remote bundles contain assets, never scripts. Load them by stable bundle name; the kit resolves dependencies, retries, references, cache, and release.
- Runtime JSON belongs under project `files/data/` and is read with `Tapcraft.content.json`. Raw files belong under `files/assets/` and use `Tapcraft.content.url`. Do not hard-code a CDN, content version, or storage path.
- Release dynamically loaded content with `Tapcraft.content.release`; clear game-owned pools in `Tapcraft.content.onLowMemory`.

Read [references/content-assets.md](references/content-assets.md).

### Runtime and platform

- One import: `import { Tapcraft } from '../tapcraft/index'` (relative to the script). `assets/tapcraft/` is generated by `npx tapcraft sync`, committed, never edited; `npm install` syncs it, and `build`/`check`/`pack` fail when it drifts. No `platform`, `saves`, AmaGDK, `./hub/*`, native bridges, ad/payment SDKs, or Cocos quit calls in game code.
- Boot order: `await Tapcraft.init()` → first loading frame → `Tapcraft.lifecycle.firstFrameReady()` → `hidePlatformLoadingScreen()` → load local core/menu → `gameReady()`.
- Exit with `Tapcraft.lifecycle.requestExit()`. Never call `game.end`, `director.end`, `game.restart`, `sys.close`, or native reflection/bridge APIs.
- Save with `Tapcraft.storage` (in memory, committed natively; `await flush()` at milestones; writes return `false` when refused). Never use `localStorage` or `sys.localStorage`. Pause gameplay and all audio for every `lifecycle.onPause` reason (`hubMenu`, `background`, `ad`, `exit`, `system`); a component that subscribes calls the returned unsubscribe function in `onDestroy`.
- Services (`lifecycle`, `storage`, `content`, `ads`, `analytics`, `system`, …) versus `Tapcraft.caps` (`haptics`, `audio`): check `available`. Every async call resolves with a result value and never rejects; handle `unavailable` and `error`.
- Wrap actual runs in `lifecycle.gameplayStart()` / `gameplayStop()` and close every pair.

Read [references/game-contract.md](references/game-contract.md) and [references/tapcraft-api.md](references/tapcraft-api.md).

### Build and verification

- Use `npx tapcraft build ios|android|all`; do not use a hand-written Cocos build configuration for a release.
- After a kit update (`npm i com.amanotes.tapcraft-kit@latest`, which syncs `assets/tapcraft/`), commit `assets/tapcraft/` and rebuild.
- Run `npx tapcraft check` and resolve every error. Review every warning rather than suppressing it.
- Test through `npx tapcraft serve` on the internal app, including airplane mode, background/resume, ads, exit/relaunch with saves, remote failure, frame time, and memory return.
- Pack target is 8 MB, hard limit 15 MB. First frame target is 1.5 s, playable target 3 s offline, gameplay p95 17 ms, and peak memory target 300 MB on low-tier devices.

Read [references/dev-loop.md](references/dev-loop.md) and [references/performance.md](references/performance.md).

### Publishing

- Only the TapCraft MCP writes platform storage. Do not upload with Firebase, GCS, or custom scripts.
- Build → check → upload `remote/`, `data/`, and any `assets/` used by `Tapcraft.content.url` with MCP → `tapcraft pack all` (writes `tapcraft.json`, protocol 2) → create builds → create/update version → show final state → ask before publish.
- A kit 1.x game is hidden by the 2.0 app until rebuilt with kit 2 and republished as a new build and version.
- Always ask before `publish_version`, `unpublish`, `delete_files`, `delete_version`, `move_game`, or changing membership/roles.
- The MCP prompts and resources are authoritative when they differ from prose bundled in this plugin.

Read [references/publishing.md](references/publishing.md).

## Completion standard

A change is not done because it works in Preview. It is done when the native TapCraft build passes `tapcraft check`, remains playable offline from the pack, handles remote failure, obeys lifecycle/storage/exit rules, stays within budgets, and has no undocumented platform dependency.
